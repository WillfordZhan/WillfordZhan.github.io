# Agent 工具轨迹完整对话示例设计

## 背景

当前文章只展示工具轨迹，读者能看到调用步骤，但看不到调用由什么问题触发，也看不到工具完成后助手如何组织结果。示例需要补齐一次典型对话，让“用户请求、工具处理、助手回答”形成连续阅读路径。

## 目标

- 在现有文章的交互示例中加入一条用户消息和一条助手消息。
- 保留现有 Codex 风格工具轨迹及其展开、收起能力。
- 让读者不看正文说明，也能理解轨迹处于一次对话的中间阶段。

## 选定方案

采用纵向完整对话流：

1. 用户消息位于右侧，提出查询物料库存变化和最近入库情况的请求。
2. 工具轨迹位于两条消息之间，并与助手侧左边界对齐。
3. 助手结果消息位于左侧，概括已完成的查询，并明确说明存在一项未完成步骤。

文章演示中的轨迹默认展开，便于读者第一眼理解三者关系；用户仍可点击收起。真实产品继续保持“运行时展开、结束后默认收起”的既有行为，文章演示不改变产品逻辑。

## 视觉结构

- 外层使用一个浅色对话画布，统一承载三段内容。
- 用户消息使用右对齐的浅蓝气泡，并显示“用户”角色标签。
- 助手过程和结果使用左对齐布局，并显示“助手”角色标签。
- 轨迹沿用现有细时间线、灰色完成状态和琥珀色未完成状态。
- 移动端允许消息气泡占据更大宽度，避免文本被压成窄列。

## 示例文案

用户消息：

> 帮我查一下物料 A 最近的库存变化，并总结最近一次入库情况。

助手结果：

> 已完成库存、库存变化和最近入库记录的查询。其中一项历史业务记录未读取成功，但不影响本次库存结论。

示例不使用真实物料名称、库存数字、客户信息或内部系统标识，避免把演示数据误解为真实业务结果。

## 实现边界

- 只修改现有文章内的 HTML 与作用域 CSS。
- 复用原生 `<details>`，不增加 JavaScript 或第三方依赖。
- 不修改产品前端、Pi Runtime 或 Java Gateway。
- 不增加新的通用组件或样式文件。

## 异常表达

轨迹中保留一项“未完成”步骤，收起态继续显示未完成数量。助手结果必须同步说明该步骤是否影响最终结论，避免轨迹与回答互相矛盾。

## 验收方式

- 用户消息、展开轨迹、助手结果按顺序出现在同一对话画布内。
- 点击轨迹标题可以正常展开和收起。
- 桌面端和移动端均保持清晰的左右角色关系。
- Hexo 构建成功，生成页面包含三段完整结构。
- 公开文章不包含敏感域名、凭据、本地路径或客户专属名称。
